# D2: organizations/accounts/memberships, isolated tests only

D5-FIX1 uses `demo.example.com`, verified with the unchanged authentication schemas. D2 checks the exact current deterministic email plan on receipt verification, rejecting old-domain datasets even if signed, without modifying existing accounts or credentials. PLAN_DIGEST still describes the same quotas; user row hashes and dependent receipt signatures bind the new emails. See D5.md for current results.

D6-FIX1 changes the first planned identity to Rancho El Encino Demo / RED01 / rancho-el-encino-demo, retaining the same five roles and quotas. Emails use red01.01–red01.05@demo.example.com. PLAN_DIGEST now changes because identity fields changed, invalidating receipts from the previous Roble demo plan without adopting or updating any preexisting RER organization or account. Signed-parent chaining, row inventories and protected snapshots remain mandatory.

The management command is unchanged and still rejects `--write`, even with its environment flag. No local writer is enabled. D1's environment, path, manifest and SQL guards remain unchanged.

`create_d2()` is an internal component restricted to `config.settings.demo_d2_testing`. That settings module creates a uniquely named `agrocore-d2-*` temporary directory; Django's test runner creates a real SQLite test database named `disposable.sqlite3` there. Outside the test runner NAME is `:memory:` and the writer rejects it. The guard also checks the actual connection identity, reuses D1's file guards, and refuses an outer transaction. Models/services/frontend are untouched.

Codes/slugs/emails use the D1 plan; role order is explicit and deterministic. UUIDs and passwords are independently random. User emails are under `demo.example.com`. Existing organizations or accounts, including inactive records, are never adopted by name/prefix. A single atomic transaction creates all 5 organizations, 30 users and 30 memberships. Organization candidates receive full_clean before the existing create service. Users receive field and password validation, create_user hashing, and no staff/superuser rights. Memberships receive full_clean and a single active default relationship. Each organization records dataset/stage/run UUID provenance in its description.

The D2 receipt is intentionally stage-specific (`D2-complete`), not a D1 full-ranch completion receipt. It records every created UUID, immutable row digests, run identity and protected UUID under an HMAC signature; role quotas are verified against the deterministic D2 plan. No farm/lot/animal/domain pipeline is implemented. Repetition requires the original authenticated encrypted bundle and signing key; any row change, lost receipt, partial dataset, wrong role or additional/cross membership rejects without repair or password rotation. Password verification uses the stateless Django hash checker without a setter, so it never upgrades existing hashes during a repeat/dry-run.

## Credential delivery

Passwords are generated by secrets.token_urlsafe, validated with Django and stored as Django hashes. The bundle contains credentials plus signed receipt, encrypted with Fernet authenticated encryption from the already available `cryptography` package. No dependency was installed. If that package is unavailable, delivery fails closed; there is no plaintext fallback. The independent encryption key and signing key are supplied by the caller, never stored beside/in the bundle or printed.

EncryptedTestDelivery only accepts a directory inside the disposable test root. Exclusive pending-file creation, flush/fsync and Windows no-overwrite rename protect against accidental overwrite. No normal execution output contains credentials. Current publication implementation is Windows-specific; other platforms fail closed. The real local delivery policy, external key custody and ACL certification remain future requirements; this is not a production/local delivery tool.

Stage errors roll back the database. A pending file left after rollback is unconfirmed and cannot trigger reseeding. Publication errors after commit preserve the pending encrypted bundle. Recovery verifies all signed rows and checks the delivered passwords against committed hashes, then publishes the same bundle without creating rows or passwords. Dry-run can verify that state but never publish. Lost keys, damaged bundles or ambiguous pending/final files stop for manual investigation. SQL and filesystem commits are not jointly atomic; the staged-before-commit protocol handles the tested failure points, but real crash/power-loss durability and ACLs are not certified.

Preexisting Organization/User/Membership rows are snapshotted and checked before and after staging; discrepancies cause rollback. Tests additionally preserve a protected existing farm/lot and check every domain table has no new rows. The protected organization in tests is a disposable fixture, not the existing Rancho los Hermanos database.

## Verification commands

```
python -B manage.py test apps.organizations.tests_demo_d2 --settings=config.settings.demo_d2_testing
python -B manage.py test apps.organizations.tests_demo_d1 --settings=config.settings.demo_testing
python -B manage.py check --settings=config.settings.demo_d2_testing
```

The D2 runner applies migrations only to its disposable SQLite file, never the existing database. Test PBKDF2 has reduced iteration cost solely within the test class; random salts, password validation and Django verification are real, while runtime defaults remain unchanged. D1 tests continue using separate disposable fixture files with ORM access forbidden. An empty temporary root is removed at process exit; an unexpected leftover file is never recursively removed by settings cleanup.

D3 may now be developed against disposable databases. It must retain the local command write prohibition, verify catalogs, reserve automatic calves, extend stage-specific receipts and the global transaction, and certify tenant FKs/protected domain snapshots before any later real execution. D2 is not certification for D3-D5.
