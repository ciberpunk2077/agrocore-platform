# D3: disposable farms, lots and direct animals only

`create_d3` is an internal test-only component. It uses the existing D2 disposable-file/environment guard and D1 path/mutex guards. The real command and its `--write` prohibition are unchanged. No new local execution path exists. Models, services, frontend and existing credentials are not changed.

## Preconditions and integration

D2 must already be complete and published, with its encrypted credential bundle and original signing key available. D2 receipt/account/membership verification runs before D3. D3 requires a separate delivery directory under the same disposable test root, using the existing authenticated encryption component. It never replaces the D2 bundle or generates credentials.

The caller must provide exact species and breed codes. The D6-FIX1 demo plan uses BOV/HOL, matching the local catalog codes; breed is resolved by `(species, code)`, never approximate names or first-row fallback. RANCH, F, M and ACTIVE must exist and be active. D3 does not create, reactivate or repair any catalog. Tests explicitly prepare BOV/HOL and required-code fixtures only in the disposable database. Catalog identities are signed and rechecked on repeats. D4 requires separate weighing/reproductive/production catalog preflight.

Every create uses an active default OWNER RequestContext with its own organization/user/membership, checked by the actual operation policy. FarmService, LotService and AnimalService receive their real create schemas. An existing domain row in a demo tenant without a valid D3 receipt is a collision/partial dataset, even if inactive or differently named. D3 never adopts or updates it.

## Quotas and preparation

Codes are deterministic within each tenant: D3-F01, D3-L01 and D3-A0001 sequences. Lots are distributed evenly across the requested farms. UUIDs are generated by the real models/services and recorded in the signed inventory.

All direct animals initially have ACTIVE status. Each organization has `2 * reserved + 6` adult females aged at least four years and two older adult males; remaining animals include juveniles and at least two existing calves. Adults are created before descendants. Parent gender, tenant and strictly earlier birth dates guarantee an acyclic genealogy. Existing calves inherit their mother's lot; automatic-calf mothers are disjoint from existing calves' mothers. Ordinary Animal writes use UTC for date validation, so the planning date is the earlier of tenant business_today and UTC today, satisfying both existing contracts without modifying clocks or validators.

Lot capacity is initial planned occupancy + automatic births allocated through the reserved mothers' current lots + two spare places. D3 explicitly verifies capacity and per-tenant quotas; it does not assume services enforce maximum occupancy. D4 must honor the reserved mother UUIDs/location or recompute a safe capacity plan before changes. No automatic calves are created in D3; 293 + 32 = 325 after D4.

## Inventory, rollback and delivery

The stage-specific signed D3 receipt binds to the original D2 receipt digest. It includes all Farm/Lot/Animal row fields and UUIDs (tenant, farm, lot, species, breed, gender, status, parents and dates), catalog identities, adult male/female UUIDs, existing calf UUIDs and the 32 automatic mother reservations. It is not a full-ranch or D4-complete receipt.

One D3 transaction spans all five tenants. All preexisting organization/account/membership/domain rows and relevant catalogs are snapshotted, compared before and after staging, and any change triggers rollback. D4 tables must remain unchanged and no D4 record may exist in demo tenants at this stage. On failure in farm/lot/animal creation or staging/commit, D3 requests rollback and leaves D2 unchanged. D2 was already committed and is not deleted by a D3 rollback.

Encrypted publication occurs after commit. Failure retains the pending receipt for verified recovery; repeat publishes the same ciphertext without creating records or regenerating credentials. A pending receipt for rolled-back/missing rows is rejected. Modified rows, extra rows, missing receipt, invalid signature, changed catalogs or partial quotas reject without repair. Dry-run performs checks and plan computation only; it never stages or publishes.

## Testing and remaining limits

Run:

```
python -B manage.py test apps.organizations.tests_demo_d1 apps.organizations.tests_demo_d2 apps.organizations.tests_demo_d3 --settings=config.settings.demo_d2_testing
python -B manage.py check --settings=config.settings.demo_d2_testing
```

Only the disposable SQLite test file receives schema migrations or fixture writes. No real data is seeded. Publication remains Windows-only; real key custody, ACLs and power-loss durability remain uncertified as documented in D2. D4 must add its own chronology, catalog checks, transitions and stage receipt, preserving the real command lockout. No weights, vaccinations, movements, breeding, pregnancies, births or production are implemented here.
