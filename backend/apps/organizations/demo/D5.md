# D5 — Certificación exclusivamente desechable

El comando `seed_demo_ranches` conserva el bloqueo incondicional de `--write`.
No hay adaptador de activación local. D2/D3/D4 siguen exigiendo el settings
`config.settings.demo_d2_testing` y el archivo SQLite temporal exacto del runner.
Fuera del runner, ese settings utiliza `:memory:` y los escritores lo rechazan.
No se han modificado modelos, servicios, frontend ni migraciones.

## Verificaciones

`tests_demo_d5.py` crea un grafo independiente de Rancho los Hermanos con usuario,
membership, finca, dos lotes, animales, pesaje, vacunación, movimiento, reproducción,
gestación, parto, cría y producción **antes de D2**. Compara snapshots completos
después de D2–D4, sin imprimir hashes de contraseñas ni credenciales.

Las pruebas utilizan el ORM, todos los selectors de recursos y el API montado
mediante Django Client y middleware real. Las sesiones JWT son independientes
para las cinco organizaciones. Se comparan conjuntos exactos de UUID en listados,
detalles propios, 404 para detalles ajenos e historiales/timeline ajenos vacíos.
Se ejercitan los cinco roles y la denegación HTTP de escritura para VIEWER.
Los JWT directos permiten verificar aislamiento de recursos; **no prueban que el
login con las credenciales demo funcione**. Una prueba separada exige login real.

Se comprueban cuotas, genealogía, fechas, ubicación, capacidad, ventas, último peso,
OneToOne, Pregnancy/Birth/Calf, unidades, Dashboard y fecha civil operativa.
Las repeticiones de D2/D3/D4 se ejecutan bajo una barrera que rechaza SQL distinto
de SELECT/control de transacciones y prohíbe nuevo staging. La recuperación
simulada de publicación se prueba en cada fase sin nueva contraseña ni SQL de
escritura y conserva el mismo ciphertext.

Los tests previos D1–D4 completan la cobertura de colisiones, catálogos,
transacciones fallidas, manifiestos parciales, CLI y mutex entre procesos.
No se considera la cobertura de esos casos aprobada hasta completar su ejecución.

## Correcciones de seguridad dentro del alcance

* D2 ahora comprueba todos los modelos administrados antes/después del staging,
  incluyendo registros de dominio preexistentes. Una prueba inyecta una mutación
  de una finca protegida y exige rollback de todo D2.
* `windows_acl.py` establece una DACL privada e inheritable sobre directorios
  nuevos de entrega. Solo permite acceso completo al SID del proceso y SYSTEM.
  Verifica las ACE reales en directorio y archivos antes de leer/publicar.
  Rechaza ACL desconocidas; no repara silenciosamente una entrega existente.
  El archivo cifrado se crea exclusivo dentro del directorio privado, se sincroniza
  y se publica mediante rename Windows sin sobrescritura.
* Una prueba modifica una ACL Windows real del directorio temporal, verifica el
  rechazo y restaura únicamente esa fixture para poder eliminarla al terminar.
  Otra simula un fallo de inspección de ACL y exige cero cambios en la base.
* Cifrado autenticado Fernet y firma HMAC usan claves externas independientes.
  Las pruebas retienen claves solamente en memoria; no existe custodio persistente
  certificado, entrega de contraseñas en logs ni fallback en texto plano.

## Bloqueante original y D5-FIX1

Antes de D5-FIX1, el plan D2 exigía `@demo.invalid`. Los schemas LoginSchema/UserSchema
utilizan EmailStr, cuyo validador rechaza el dominio reservado `.invalid`.
Esto provocó login 422 y un error al serializar el usuario demo en
`/api/common/context`. Emitir JWT directamente no resolvía ese defecto.

D5-FIX1 autoriza sustituir únicamente el dominio por `demo.example.com`.
LoginSchema y UserSchema reales aceptan `owner.roble@demo.example.com` sin
cambios de EmailStr, modelos, servicios ni schemas. Los prefijos deterministas,
roles, cuotas y procedencia se conservan. Las pruebas de aceptación se mantienen
y ahora verifican login JWT/contexto de los 30 usuarios demo, sesiones independientes
de cinco tenants y permisos VIEWER mediante tokens obtenidos en login real.

PLAN_DIGEST describe las cuotas y no contiene emails, por lo que permanece igual.
Los hashes de filas de User y las firmas/digests encadenados D2/D3/D4 sí reflejan
los emails nuevos. D1 busca exclusivamente el plan de emails vigente. D2 verifica
el conjunto exacto de sus 30 emails contra ese plan: incluso un manifiesto antiguo
con firma e inventario válidos se rechaza sin modificar registros ni credenciales.
No existe migración, adopción ni reparación automática de datasets anteriores.
Las menciones restantes a `demo.invalid` son históricas o pruebas negativas.

## Reproducción segura

Desde `backend`, con el Python del entorno virtual existente:

```
../.venv/Scripts/python.exe -B manage.py test apps.organizations.tests_demo_d1 apps.organizations.tests_demo_d2 apps.organizations.tests_demo_d3 apps.organizations.tests_demo_d4 apps.organizations.tests_demo_d5 --settings=config.settings.demo_d2_testing --verbosity 1
../.venv/Scripts/python.exe -B manage.py check --settings=config.settings.demo_d2_testing
../.venv/Scripts/python.exe -B manage.py test --settings=config.settings.demo_d2_testing --verbosity 1
```

Cada proceso usa su propia carpeta `agrocore-d2-*` bajo TEMP. El runner crea y
migra exclusivamente esa SQLite desechable. Las pruebas de migraciones de
catálogos utilizan otro alias SQLite en memoria; las fixtures D1 usan archivos
temporales independientes. No ejecutar estos comandos con settings local/base.

La base persistente configurada por este repositorio es `backend/config/db.sqlite3`;
`backend/db.sqlite3` no existe en el workspace inspeccionado. Ninguna es destino
de estas pruebas. No es necesario abrir la base persistente para certificar fixtures.

## Límites de certificación

Los fallos de servicio, commit, staging y publicación son inyectados, no cortes
reales de energía. No se certifican atomicidad entre SQLite/filesystem ante caída
del sistema, recuperación con pérdida de claves, robo de la sesión Windows,
administradores capaces de tomar propiedad, otros volúmenes/usuarios Windows,
almacenamiento persistente de claves ni activación local.
Un futuro READY autorizaría únicamente diseñar dicha activación; nunca sembrar
datos reales ni habilitar el comando.
